# 졸업전시 팀 워크스페이스

정적 HTML / CSS / JavaScript 웹앱. 앱 원본은 `dist/`, GitHub Pages용 결과물은 `npm run build`가 만드는 `site/`에 있습니다.

## GitHub 배포와 팀 공유 저장소

배포 빌드는 esbuild가 Supabase 클라이언트를 포함해 `site/`에 묶고, 접속 설정은 빌드 때만 생성합니다. Supabase 설정이 없는 로컬 미리보기는 기존 브라우저 저장 방식으로 계속 동작합니다.

1. Supabase에서 프로젝트를 만들고 `supabase/schema.sql`을 SQL Editor에서 실행합니다. DB 없이도 배포되지만, 각자 브라우저 저장 모드로 동작합니다.
2. 실제 팀원 이메일 4개를 `public.team_members`에 이름과 함께 등록합니다. 이 목록에 있는 계정만 로그인할 수 있습니다.
3. Supabase Authentication URL 설정에서 배포 주소와 로컬 주소 `http://localhost:4173`를 허용합니다. GitHub Pages 주소 예시는 `https://ysy6631y.github.io/graduation-exhibition-dashboard/`입니다.
4. GitHub 저장소 Settings → Secrets and variables → Actions에 `SUPABASE_URL`, `SUPABASE_ANON_KEY`를 등록합니다. 브라우저 공개 키만 사용하며 `service_role` 키는 입력하지 않습니다.
5. 저장소 Settings → Pages에서 배포 원본을 GitHub Actions로 설정합니다. `main`에 push하면 자동 배포되며, Actions에서 수동 실행도 할 수 있습니다. Supabase secret이 비어 있으면 사이트는 공개되지만 데이터는 브라우저별로 분리됩니다.

첫 번째 팀 로그인 때 그 브라우저의 기존 작업을 공유 DB의 초기 데이터로 저장합니다. 이후 다른 팀원은 공유 DB 데이터를 읽고, 변경 내용은 Supabase Realtime으로 갱신됩니다. 서버의 revision 비교와 3방향 병합으로 서로 다른 항목의 동시 편집을 합치고, 같은 필드의 충돌은 저장을 거부합니다. RLS 정책은 팀 이메일 allowlist를 확인합니다.

공개 저장소와 GitHub Pages 사이트는 누구나 열 수 있습니다. Supabase를 연결하면 팀 이메일 로그인 및 DB 정책으로 작업 데이터를 보호할 수 있습니다. DB가 비어 있는 빌드는 앱 상단에 브라우저별 저장 안내를 표시합니다.

`npm run build`는 Supabase 설정이 있으면 팀 공유 DB, 없으면 브라우저별 저장 모드로 결과물을 만듭니다. `npm run build:pages`는 DB 설정이 빠지면 실패합니다.

## 로컬 실행

```sh
npm run preview
```

http://localhost:4173 을 엽니다. 기존 로컬 서버가 실행 중이면 그대로 새로고침하면 됩니다.

## 검증

```sh
npm install
npm test
```

테스트는 DOM에서 실제 등록·상세수정·필터·완료/되돌리기 이벤트를 실행하고, 저장 실패 및 기존 데이터 보존을 검증합니다. 브라우저 렌더링의 시각 검증을 대신하지 않습니다.

## 저장과 데이터 보존

- 기존 `grad-exhibition-dashboard-v1` 키를 그대로 읽습니다.
- 기존 작업 ID, 메모, 날짜, 자료 링크 및 알 수 없는 필드를 보존합니다.
- 첫 저장 전에 원본 전체를 `grad-exhibition-dashboard-v1-before-v2` 키에 백업합니다.
- 기존 단일 `due` 날짜는 시작일/마감일로 읽습니다. 날짜 미정 작업에는 임의 날짜를 넣지 않습니다.
- 저장 실패 시 현재 입력 창과 이전 저장 데이터를 유지합니다.
- 같은 출처의 다른 탭과는 storage 이벤트로 동기화합니다. 지연된 이벤트는 현재 저장소를 다시 읽어 처리합니다.
- 저장은 [Web Locks](https://www.w3.org/TR/web-locks/)로 순서를 보장하고, 미지원 환경에서는 IndexedDB read/write 트랜잭션을 잠금으로 사용합니다. 두 방식 모두 사용할 수 없으면 안전하지 않은 저장으로 대체하지 않고 오류를 표시합니다.
- 편집 시작 시점, 내 변경사항, 최신 저장값을 비교해 바뀐 항목만 합칩니다. 서로 다른 항목은 병합하고 같은 항목의 충돌, 수정/삭제 충돌, 날짜 조합 오류는 저장하지 않습니다.
- 되돌리기에도 같은 비교를 적용합니다. 나중에 들어온 메모는 보존하며, 다른 탭의 최신 상태를 되돌리기로 덮어쓰지 않습니다.
- 저장 중 중복 제출을 방지하고, 충돌 시 입력 창을 유지합니다.
- 작업마다 여러 담당자를 선택하고 개인별 `진행 중 / 확인 필요 / 완료`를 저장할 수 있습니다. 전체 작업 상태는 별도로 유지합니다.
- 기간을 수정하면 겹치는 미완료 일정과 담당자, 같은 담당자 겹침을 편집 화면에서 미리 보여줍니다. 저장된 날짜 변경은 팀원별 기록에 변경 전·후 기간으로 남습니다.
- 기존 단일 담당자는 개인별 상태를 가진 담당자 목록으로 읽으며, 기존 `owner` 값도 호환용으로 유지합니다. 담당자 필터는 공동 담당자 전원을 대상으로 합니다.
- 서로 다른 담당자의 상태 변경은 동시에 합치고, 같은 담당자의 서로 다른 상태 변경은 충돌로 처리합니다.
- 진행 현황은 `작업별 / 개인별`로 볼 수 있습니다. 개인 상태 변경은 개인별 보기에, 전체 상태 변경은 작업별 보기에 반영합니다. 완료 직후에는 완료 표시를 켜서 변경한 카드를 확인할 수 있게 합니다.
- `팀원별 기록`에서 상태 변경 이력과 직접 작성한 작업 메모를 모아 봅니다. 기록은 작업 변경과 같은 저장 단위로 함께 저장되며, 되돌리기도 별도 이력으로 남습니다. 완료 숨김이나 작업 삭제로 기존 기록을 지우지 않습니다.
- 과거 이력은 추측해 생성하지 않습니다. 기록에 표시되는 팀원은 상태의 대상 또는 메모에서 선택한 사람이며, 로그인 없는 현재 버전에서는 실제 조작자의 신원을 인증하지 않습니다.

검증에는 네 개의 독립 DOM 화면과 공유 저장소/잠금 시뮬레이터를 사용합니다. 네 화면의 동시 등록 80건, IndexedDB 대체 경로 160건, 같은/다른 필드 편집, 삭제 충돌, 되돌리기, 저장 알림 지연을 확인합니다. 실제 브라우저 엔진과 여러 기기의 네트워크 동시 접속은 별도 검증이 필요합니다.

공유 저장 코드는 Supabase 인증·DB·실시간 동기화로 구현되어 있습니다. 다만 프로젝트 URL/공개 키와 실제 팀 이메일을 등록하기 전에는 현재 미리보기가 로컬 브라우저 저장 모드로 실행됩니다. 로컬 모드는 새로고침에는 유지되지만 팀원 간 공유는 되지 않습니다. 팀 공유 배포 전 위 Supabase 설정이 필요합니다.

## 구성

- `dist/core.mjs`: 저장, 데이터 호환, 날짜 겹침 계산, 변경 이력
- `dist/app.js`: 공통 렌더러, 필터, 등록, 상세 편집, 일정 영향 미리보기, 드래그, 저장 피드백
- `dist/styles.css`: 디자인 토큰, 컴포넌트, 반응형, 접근성 모션 설정
- `tests/workspace.test.mjs`: 핵심 사용자 흐름 및 데이터 보존 검증
- `tests/activity.test.mjs`: 개인/전체 상태 보드, 완료 직후 표시, 작업 기록, 기록 동시 저장과 복원 검증

로컬 미리보기는 `npm run preview`로 실행할 수 있습니다. 팀 공유 배포는 Supabase 및 GitHub Actions secret 설정 후 진행해야 합니다.
